### Как работать с репозиторием
1. В вашем GitHub-аккаунте автоматически создастся репозиторий `de-project-sprint-3` после того, как вы привяжете свой GitHub-аккаунт на Платформе.
2. Скопируйте репозиторий на свой локальный компьютер, в качестве пароля укажите ваш `Access Token` (получить нужно на странице [Personal Access Tokens](https://github.com/settings/tokens)):
	* `git clone https://github.com/{{ username }}/de-project-sprint-3.git`
3. Перейдите в директорию с проектом: 
	* `cd de-project-sprint-3`
4. Выполните проект и сохраните получившийся код в локальном репозитории:
	* `git add .`
	* `git commit -m 'my best commit'`
5. Обновите репозиторий в вашем GutHub-аккаунте:
	* `git push origin main`

### Структура репозитория
1. Папка `migrations` хранит файлы миграции. Файлы миграции должны быть с расширением `.sql` и содержать SQL-скрипт обновления базы данных.
2. В папке `src` хранятся все необходимые исходники: 
    * Папка `dags` содержит DAG's Airflow.

## Пайплайн

`get_report → bootstrap_report → get_increment → load_increment → update_marts`

1. Получить или повторно использовать исходный отчёт.
2. Однократно загрузить его продажи и пересчитать витрины; маркер отчёта в
   `staging.etl_reports` сохраняется в той же транзакции. Повторный запуск пропускает этап.
3. Запросить инкремент за логическую дату Airflow `ds`.
4. Проверить CSV, затем в транзакции заменить срез staging за день.
5. Обновить измерения через upsert, заменить продажи за день и пересчитать всю неделю.

Планирование — `@daily`, `catchup=False`, `max_active_runs=1`. Включайте DAG после
настройки Connections/Variables. Для исторической даты используйте логическую дату
запуска в интерфейсе или `airflow dags test sales_mart YYYY-MM-DD`. Для загрузки пропущенных
дней выполняйте их последовательно. API может не отдавать отчёт за текущий день —
расчёт ведётся за завершённый день согласно логической дате запуска.

## Статусы и backward compatibility

Миграция проставляет историческим строкам `mart.f_sales` статус `shipped`.
CSV без `status` также считается отгрузкой; пустое значение трактуется как старый
формат. Неизвестный статус вызывает ошибку до удаления ранее загруженного среза.

Факт сохраняет транзакционную гранулярность: одна строка staging = одна строка
`f_sales`, без агрегации по дню. Для `refunded` количество и сумма равны `-ABS(...)`:
уже отрицательный возврат не станет положительным. Total revenue считается как
`SUM(payment_amount)`, включая отрицательные возвраты.

`uniq_id` — идентификатор исходной строки, а не номер заказа: отдельного order_id
в контракте нет. Точные дубли CSV удаляются, конфликтующие строки с одним uniq_id
отклоняются. Цена, activity и research не участвуют в новых витринах и не загружаются
этим DAG.

## Правила retention

Гранулярность: ISO-неделя × `item_id`. `period_id` — номер ISO-недели, а дополнительный
`period_start` — понедельник недели. Первичный ключ `(period_start,item_id)` не смешивает
одинаковые номера недель разных лет.

Внутри недели и категории:

- new: ровно одна транзакция `shipped` у клиента;
- returning: больше одной транзакции `shipped`;
- refunded_customer_count: уникальные клиенты с хотя бы одним возвратом;
- new/returning revenue: сумма отгрузок соответствующей категории (gross revenue);
- customers_refunded: количество транзакций возврата, не количество единиц товара.

Клиент с покупкой и возвратом входит в свою покупательскую категорию и одновременно
в refunded. Клиент только с возвратом входит только в refunded. Эти группы не являются
взаимоисключающими. Денежная сумма возвратов доступна в `f_sales` с отрицательным знаком.

## Идемпотентность и исправленное воскресенье

Повторная загрузка удаляет прежний дневной срез и вставляет актуальный. После этого
retention заменяется за всю соответствующую неделю, поэтому обновляются и категории
клиентов, которые изменились после исправления воскресенья. Dimensions обновляются
через ON CONFLICT. Продажи и retention публикуются одной транзакцией: при ошибке
предыдущая версия mart остаётся доступной. Staging может содержать новую версию до
повторного успешного запуска `update_marts`, что соответствует разделению слоёв.

В контракте предполагается, что инкремент содержит полный актуальный срез указанного
дня; данные чужой даты отклоняются. Перенос одной транзакции между разными датами
требует повторной загрузки обеих дат. Одновременный запуск других DAG, меняющих эти же
таблицы, не поддерживается — на стенде этот пайплайн должен владеть ими.

## Ограничения трактовки задания

В источнике нет отдельного номера заказа: число покупок определяется числом уникальных
транзакций `uniq_id`. Если источник начнёт присылать несколько товарных строк одного
заказа с общим order_id, классификацию new/returning нужно будет считать по этому order_id.
